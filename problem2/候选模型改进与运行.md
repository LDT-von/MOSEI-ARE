# 问题二：文本蒸馏与条件融合候选实验

状态：**仅实现候选代码，尚未训练；没有新分数，也没有替换当前交付权重。**

## 为什么先改这里

当前 `models/gap_slot_emo.py` 的文本分支是随机初始化的 30,522×128 词嵌入加一层 Transformer。附件 2 只有 3,395 条训练样本。相比之下，[Coupled Mamba](https://papers.nips.cc/paper_files/paper/2024/file/6e09c213ac18d6375704a4f3ea75c4f8-Paper-Conference.pdf) 的 MOSEI 实验使用 BERT 文本特征、16,326/1,871/4,659 的切分和 5 次运行均值；[ECA-CMF Net](https://www.mdpi.com/2079-9292/15/11/2420) 使用 DeBERTa-v3-base、语音和视觉专用编码器与条件调制融合。论文分数不能直接作为本赛题 4,850 条数据的可达目标，论文 F1-Score-3 也不能直接等同于本仓库的 `f1_macro`。

附件 2 的 `train.text` 提供 50×768 的预计算文本特征，附件 3 **没有**该字段。因此候选模型仅在训练时用这个字段指导小型文本编码器；验证、测试、附件 3 推理仍只用 `text_bert` token ID。提交包不需要原始 768 维特征或大型预训练语言模型。候选模型继续使用原来的 50 位置、Slot Attention、局部补偿和双任务头；没有照搬 Coupled Mamba 的状态空间模块。

## 三步独立对照

| 配置 | 相对当前 Arm C 的变化 | 损失 |
| --- | --- | --- |
| `candidate_text.json` | 训练时文本蒸馏；推理骨架不变 | `CE + 0.5 Huber + 0.15 cosine` |
| `candidate_cmf.json` | 在上一步基础上增加按模态可用性和覆盖率调节 slot 摘要的条件调制；初始化为恒等映射 | 同上 |
| `candidate_cmf_balanced.json` | 在上一步基础上按训练集类频率的平方根加权 CE | `weighted CE + 0.5 Huber + 0.15 cosine` |

蒸馏目标是将 `train.text` 经固定随机投影映射到 128 维后的**方向**；只对当前未遮挡的文本位置计算余弦损失。投影与小模型参数保存在候选权重中。条件调制是借鉴 ECA-CMF 的条件缩放/偏移思想，并未实现该论文的完整网络。类别加权用于检验中性类别召回能否改善，可能降低总准确率，需要验证集判断。

旧版 `models/gap_slot_emo.py` 与 `problem2/data.py` 保持原样，已有 `best.pt` 的来源校验和加载路径不变。候选实验使用全新输出目录，旧报告不并入候选成绩。

## 用户启动的命令

在 `C:\Users\栋栋\Desktop\E题\MOSEI-ARE` 仓库根目录运行。先以同一个 seed 做三步检查，全部只查看 `valid`：

```powershell
python -m problem2.scripts.run train --arm C --config problem2/configs/candidate_text.json --seed 42 --device cuda --output problem2/outputs/candidate_text_seed_42
python -m problem2.scripts.run train --arm C --config problem2/configs/candidate_cmf.json --seed 42 --device cuda --output problem2/outputs/candidate_cmf_seed_42
python -m problem2.scripts.run train --arm C --config problem2/configs/candidate_cmf_balanced.json --seed 42 --device cuda --output problem2/outputs/candidate_cmf_balanced_seed_42
```

每组训练会保存逐 epoch 的 clean/mixed 验证指标、各项训练损失、配置与来源哈希，以及 `best.pt`。已有输出目录会被拒绝覆盖。训练结束时脚本检查单个 checkpoint 是否超过 50 MB；最终压缩包仍须另外检查总大小。

```powershell
python -m problem2.scripts.run evaluate --checkpoint problem2/outputs/candidate_text_seed_42/best.pt --split valid --grid --device cuda
python -m problem2.scripts.run evaluate --checkpoint problem2/outputs/candidate_cmf_seed_42/best.pt --split valid --grid --device cuda
python -m problem2.scripts.run evaluate --checkpoint problem2/outputs/candidate_cmf_balanced_seed_42/best.pt --split valid --grid --device cuda
```

先对照旧 Arm C seed=42 的**同一验证集** clean/mixed 宏 F1、Accuracy、中性 recall、MAE 与 27 条件网格；再看每一步相对前一步的增量。单个 seed 的改善只算探索。若某步骤有希望，用完全相同的配置给旧版和候选版补跑至少 3 个匹配 seed，按 seed 报告均值与离散度；选模型和 seed 只看 `valid`。先前曾用 `test_clean_f1` 作为 seed=2024 替换理由，所以现有 test 已参与过选择，今后的 test 数字也不能再称为完全独立的盲测证据。

补跑时固定 seed 列表，例如 `42, 1234, 2026`，旧版用 `problem2/configs/default.json`，候选版用选中的配置；每次的 `--output` 路径必须唯一。例如旧版第一组：

```powershell
python -m problem2.scripts.run train --arm C --config problem2/configs/default.json --seed 42 --device cuda --output problem2/outputs/recheck_base_seed_42
```

候选版本将 `--config` 换成选中的候选 JSON，`--output` 换成对应候选目录；三组都完成后再比较相同 seed 的验证集差值，避免单独挑一个幸运 seed。

只有在验证集选定唯一配置和权重后，才运行对应权重的 `test` 与附件 3 推理。问题三解释入口复用相同 checkpoint，但新解释结果也需重新生成，不可沿用旧权重的证据 JSON。
